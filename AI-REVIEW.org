* TODO P2b — the brand-color gap found by the 2026-10-27 compliance audit
  - [ ] AGENTS.md states "components carry zero hard-coded colors", and it is
    true for IDENTITY colors (every brand value reaches a component through
    the `@theme inline` map in app/src/app.css: `--color-primary/accent/bg/
    surface/text` -> `--brand-*`). It is NOT true for STATUS colors: 16
    palette classes (15 `*-red-*` + 1 `bg-emerald-500`) sit in
    app/src/components/RecordForm.svelte, DataTable.svelte, ErrorBanner.svelte,
    app/src/pages/Login.svelte, Branding.svelte, Modules.svelte.
    Why they survived: brand.json's closed schema (plugin/src/admincraft/
    branding.py `ALLOWED_COLOR_KEYS`) carries five identity keys and no
    danger/success slot, so a rebrand cannot move an error red — and the
    shades are used as a translucency ramp (bg at /5..10%, border at /30..40,
    text at 100..400), so collapsing them onto one token is a VISUAL change
    that must be judged in a browser, not by a green suite.
    Decide before fixing: (a) add `danger`/`success` to the brand schema —
    touches server validator, `brandToCss`/`render_css` twins and their pinned
    matrix counts; or (b) keep status hues fixed and define them once in
    app/src/app.css as `--color-danger`/`--color-success`, which makes the
    sentence above true by construction ("components carry zero hard-coded
    colors" = no color literal outside the theme block).

* DEBUGGING WAR STORY (read before touching Svelte reactivity)
  Two dev-mode traps cost hours here; both look like "the app froze at first
  render / store subscriptions never update":
  1. Vite dep-optimizer can emit TWO svelte internals instances (different
     ?v= hashes) when svelte/store is discovered lazily. Store subscriptions
     then register with a dead effect registry. Fix: optimizeDeps.include all
     svelte entrypoints (see app/vite.config.ts) + Cache-Control: no-store.
  2. A crash ANYWHERE inside a render flush (e.g. Svelte's
     each_key_duplicate from a nested keyed-each reusing the outer key
     variable) aborts the whole update queue silently — the last good DOM
     stays, looking exactly like broken reactivity. Instrument with
     window.addEventListener('error') and read the console BEFORE blaming
     the framework.
  3. Node >= 16 fires req.on('close') right after body 'end' — using it to
     "clean up on client disconnect" clears stream timers before their first
     tick (mock_openai.js: listen on res 'close' instead).
